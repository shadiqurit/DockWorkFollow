আপনার requirement অনুযায়ী এটাকে শুধু **Document Forwarding** হিসেবে design করলে পরে আবার rewrite করতে হবে। এটাকে **configurable Workflow + Approval + Review + Distribution Engine** হিসেবে design করা সবচেয়ে ভালো হবে।

আপনার upload করা existing structure-ও আমি দেখেছি—বিশেষ করে `DF_SEQUENCE`, `DF_FORWARD_T`, `DF_FORWARDING_INS`, `PUR_ITEM`, department head এবং approval range data। Existing system-এর সবচেয়ে বড় limitation হলো `L1_EMPCODE ... L12_EMPCODE` এবং `L1_TYPE ... L12_TYPE` ধরনের fixed-column architecture। এটা এখন কাজ করলেও আপনার নতুন requirement—dynamic range approval, item expert, arbitrary review, return, delegation, post-approval distribution—এসব যোগ হলে খুব দ্রুত complex হয়ে যাবে।

আপনার বর্তমান generated document-এর page 2-তেও Created → Reviewed → Forwarded → Approved এবং প্রতিটি ব্যক্তির Remarks/Date history দেখানো হচ্ছে। নতুন design-এ এই একই output রাখা যাবে, তবে history আর L1/L2 column থেকে নয়, একটি generic transaction history থেকে আসবে। 

# 1. Recommended Architecture

আমি system-টাকে ৬টি logical layer-এ ভাগ করব:

```text
DOCUMENT
   │
   ├── Document Type
   ├── Document Data / Purchase Data
   ├── Attachments / Versions
   │
   ▼
WORKFLOW CONFIGURATION
   │
   ├── Workflow
   ├── Workflow Steps
   ├── Approval Rules
   ├── Actor Resolution
   │
   ▼
WORKFLOW INSTANCE
   │
   ├── Current Step
   ├── Assigned Employee
   ├── Pending Task
   │
   ▼
ACTIONS / HISTORY
   │
   ├── Submit
   ├── Forward
   ├── Review
   ├── Review Return
   ├── Return
   ├── Reject
   ├── Approve
   │
   ▼
FINAL APPROVAL
   │
   ▼
DISTRIBUTION
   ├── Employee
   ├── Department
   └── External Person
```

এখানে সবচেয়ে গুরুত্বপূর্ণ principle:

> **Workflow Definition আর Document Transaction কখনো একই table-এ রাখবেন না।**

# 11. দুই ধরনের Amount Rule Support করুন

এটা খুব গুরুত্বপূর্ণ।

আপনার business policy দুইভাবে হতে পারে।

### Option A — Final authority based

৳8,000:

```text

```

৳25,000:

```text

```

৳45,000:

```text

```

### Option B — Cumulative approval

এটাই corporate approval-এর জন্য বেশি common:

৳8,000:

```text

```

৳25,000:

```text

```

৳45,000:

```text
Department Head
→ Accounts Head
→ CFO
```

৳75,000:

```text
Department Head
→ Accounts Head
→ CFO
→ Executive Director
```

```text
Department Head
→ Accounts Head
→ CFO
→ Executive Director
```

বা

# 15. আপনার সবচেয়ে গুরুত্বপূর্ণ Requirement: Ad-hoc Review

ধরুন document এখন CFO-এর কাছে।

Normal route:

```text
Department Head
→ Accounts Head
→ CFO
→ ED
→ MD
```

CFO document দেখে মনে করলেন IT-এর Shadiqur-এর opinion দরকার।

তিনি:

```text
Send for Review
       ↓
Shadiqur
```

এই review normal approval route-এর part হবে না।

System:

```text
CFO Task = WAITING_REVIEW

Review Task
Reviewer = Shadiqur
Requested By = CFO
Parent Task = CFO task
```

Reviewer:

```text
Review Complete
Remarks: "Technical specification found okay."
```

তারপর:

```text
Review Task = COMPLETED

CFO Task = PENDING
```

Document আবার CFO-এর inbox-এ আসবে।

CFO তারপর:

```text
Forward
```

করলে normal path:

```text
CFO → ED
```

চলবে।

এটাই আপনার requirement-এর cleanest implementation।

# 21. Return vs Reject আলাদা রাখুন

এগুলো এক জিনিস নয়।

### RETURN

Correction দরকার।

```text
ED
 ↓
Return
 ↓
Creator / Previous Step
 ↓
Correction
 ↓
Resubmit
```

Document active থাকবে।

### REJECT

Process terminated।

```text
STATUS = REJECTED
```

সাধারণভাবে creator নতুন document/version ছাড়া continue করতে পারবে না।

আপনার case-এ range-এর পরিবর্তে threshold আরও সুন্দর হতে পারে:

```text
AUTHORITY            THRESHOLD
-------------------  ---------
Department Head       10000
Accounts Head         30000
CFO                   50000
Executive Director   100000
Managing Director    NULL
```

যদি cumulative chain হয়, engine amount পর্যন্ত step তৈরি করবে।

এটা maintain করা range-এর থেকেও সহজ।

কিন্তু different item-এর different rules থাকলে range-based master বেশি flexible।

---

# 69. Approval Configuration Priority

Purchase rule resolve করার order রাখব:

```text
1. Exact Item + Company + Location
2. Item Category + Company + Location
3. Exact Item + Company
4. Item Category + Company
5. Document Type Default
```

এতে special exception সহজ হবে।

Example:

```text
Electrical
Factory
>500,000

requires MD
```

কিন্তু অন্য item-এর default policy আলাদা হতে পারে।

---

# 70. Very Important — No Data Delete

Workflow/history table থেকে transaction delete করার privilege সাধারণ user/admin-কেও দেব না।

Correction করতে:

```text
CANCELLED
SUPERSEDED
```

status ব্যবহার করুন।

Audit system-এ physical delete avoid করা ভালো।

# 71. Final Recommended Architecture

আপনার system-এর জন্য আমি শেষ পর্যন্ত এই model-টাই recommend করব:

```text
                     CONFIGURATION
                          │
             ┌────────────┼─────────────┐
             │            │             │
        Document Type   Workflow     Approval Rule
                          │
                    Workflow Steps
                          │
                Dynamic Actor Resolver
             ┌────────────┼────────────┐
             │            │            │
          Dept Head   Item Expert    Role/User
             │
             └────────────┼────────────┘
                          │
                          ▼
                     DOCUMENT
                          │
                   Submit Document
                          │
                     Route Snapshot
                          │
                          ▼
                       TASK
                          │
            ┌─────────────┼─────────────┐
            │             │             │
          Forward       Review        Return
            │             │             │
            │        Temporary Task     │
            │             │             │
            │        Return to Sender   │
            │             │             │
            └─────────────┼─────────────┘
                          │
                       Approve
                          │
                          ▼
                     DISTRIBUTION
                          │
                 Employee / External
```

## আমার recommendation

**বর্তমান `DF_MASTER + DF_SEQUENCE + L1...L12 + giant trigger` architecture-কে আর extend না করাই ভালো।**

এখন যেহেতু আপনার নতুন requirement substantially বড় হয়েছে, এই stage-এই normalized workflow engine-এ যাওয়া উচিত। এতে 12-level limitation থাকবে না, purchase amount rule hard-coded থাকবে না, item expert dynamic হবে, যেকোনো stage থেকে arbitrary review করা যাবে, review শেষে ঠিক sender-এর কাছেই ফিরবে, return/reject/version history থাকবে, approval-এর পর distribution হবে, এবং আপনার বর্তমান PDF-এর Created/Reviewed/Forwarded/Approved audit format-ও আরও cleanভাবে generate করা যাবে। 

পরবর্তী development step হিসেবে সবচেয়ে যৌক্তিক হবে **Database Design Phase**: `DF_DOCUMENT`, `DF_WORKFLOW`, `DF_WORKFLOW_STEP`, `DF_APPROVAL_RULE`, `DF_DOCUMENT_ROUTE`, `DF_TASK`, `DF_ACTION_HISTORY`, `DF_ITEM_EXPERT`, `DF_DISTRIBUTION`—এই tables-এর complete Oracle 19c DDL, PK/FK/index/constraints এবং sample procurement workflow data তৈরি করা। এরপর সেই schema-এর উপর APEX pages এবং `PKG_DF_WORKFLOW` procedure একে একে বানানো যাবে।
